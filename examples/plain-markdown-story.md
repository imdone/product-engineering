# Example HDD Story

## Problem Framing

A team needs a durable way to capture what it is trying to learn before implementation starts.

## Hypothesis

We believe a short Markdown HDD story will make the next implementation easier to review because it preserves the problem, expected outcome, evidence path, and learning loop in one place.

## Vertical Slice

- User: a product-minded engineer planning a small change.
- Behavior change: the engineer can explain what success looks like before coding starts.
- Feedback path: reviewers comment directly on the Markdown story or linked issue.
- Measurement/data capture: the story records demo notes, reviewer feedback, and the final decision.

## Acceptance Criteria

- [ ] Given a reviewer opens the story, when they read it, then they can identify the problem, hypothesis, slice, metric, and demo path.
- [ ] Given imdone is not available, when the team practices HDD, then the Markdown file still contains the artifacts needed to continue.
- [ ] Given imdone is available, when the team records a pivot, then `imdone note` can preserve the chronological decision in progress notes.

## Success Metrics

- Reviewer can summarize the hypothesis and evidence path without a walkthrough.
- The story records at least one feedback item or explicit external evidence gate before completion.
